# Reproducible build + SBOM + SLSA L2 attestation

Leah binaries on the GitHub releases page carry a four-link attestation chain
so a wary operator can answer "is this binary the one upstream published?"
without trusting the release-page UI.

Spec: `docs/engineer/specs/2026-06-10-trust-moats.md` §7 (S10 M6).

## What the workflow publishes

For every tag matching `v*`, `.github/workflows/reproducible-build.yml` emits:

- `leah-<os>-<arch>` + `leah-daemon-<os>-<arch>` — stripped, trimpath'd Go
  binaries built with `CGO_ENABLED=0 -trimpath -mod=readonly -ldflags="-s -w -buildid="`.
  Two operators running the same build on the same Go toolchain version
  produce byte-identical output.
- `leah-<os>-<arch>.spdx.json` — SBOM (SPDX-JSON) generated by syft, lists
  every module + transitive dep with its resolved version.
- `SHA256SUMS` — flat checksum file covering every artifact above.
- `SHA256SUMS.sig` + `SHA256SUMS.pem` — cosign keyless signature (Sigstore
  OIDC, no long-lived signing key). The cert binds the signature to the GHA
  workflow run that produced it.
- `leah.intoto.jsonl` — SLSA L2 provenance from
  `slsa-framework/slsa-github-generator@v2.0.0`. Records the build's source
  commit, builder ID, and entry-point workflow.

## The chain an operator verifies

```
operator-downloaded binary
        ↓ sha256
matches SHA256SUMS entry
        ↓ cosign verify-blob
SHA256SUMS.sig was issued by github.com/trilamsr/Leah workflow on this tag
        ↓ slsa-verifier verify-artifact
leah.intoto.jsonl provenance matches source repo + tag, builder is the
official slsa-github-generator
```

Break any link and the verification fails closed.

## Verifying locally

Two Makefile targets cover the operator path. Both take `LEAH_VERIFY_VERSION`
as the tag to check; both pull artifacts into `./dist-verify/<version>/`.

```sh
# Stage 1 — SHA256 only. Needs nothing but sha256sum + gh.
make verify-checksums LEAH_VERIFY_VERSION=v1.2.3

# Stage 2 — full attestation chain. Needs cosign + slsa-verifier.
brew install cosign slsa-verifier
make verify-attestation LEAH_VERIFY_VERSION=v1.2.3
```

`verify-attestation` pins the certificate identity to
`https://github.com/trilamsr/Leah/...` and the OIDC issuer to
`token.actions.githubusercontent.com`. A signature minted by any other
workflow — including a fork that pushed the same tag name to its own repo —
fails the regex check.

## Reproducing the build from source

The point of the M6 moat is that an operator who does not trust the GHA
runner can rebuild from source and diff:

```sh
git checkout v1.2.3
CGO_ENABLED=0 GOFLAGS='-trimpath -mod=readonly' \
    go build -ldflags='-s -w -buildid=' -o leah-local ./cmd/leah
shasum -a 256 leah-local
```

The resulting digest must match the row for `leah-<os>-<arch>` in `SHA256SUMS`.
Go toolchain version is pinned via `go.mod`'s `go` directive — mismatched
toolchain is the most common false-negative.

## Trust delta

| Layer            | Trusted party                    | Compromise impact                     |
| ---------------- | -------------------------------- | ------------------------------------- |
| Source           | GitHub repo `trilamsr/Leah`      | Malicious commit before tag           |
| Builder          | GitHub Actions runner            | Compromised runner image              |
| SBOM             | anchore/syft                     | Missed transitive dep                 |
| Signature        | Sigstore Fulcio + Rekor log      | Sigstore root key compromise          |
| Provenance       | slsa-github-generator (v2.0.0)   | Pinned tag — `@main` drift mitigated  |

The reproducible-build path (rebuild + diff) shortcuts the builder + SBOM +
signature rows: if the local build matches the published digest, the only
trust left is the source layer.

## Why not key-managed signing?

Long-lived signing keys require operator-side key rotation infrastructure
that Leah does not yet ship. Sigstore keyless signing binds each signature
to the OIDC identity of the workflow that produced it, recorded in the
public Rekor transparency log. Revocation = revoke the GHA workflow's OIDC
trust, which is a repo-admin action, not a key-rotation event.
